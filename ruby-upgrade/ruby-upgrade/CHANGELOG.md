# Changelog

## Unreleased
- Reworked the skill to be fully self-contained (no cross-references to `rails-upgrade` — every step, workflow, and reference now stands on its own) and to match `rails-upgrade`'s fuller directory structure instead of the leaner `upgrade-cleanup`-style layout: added `version-guides/` (2.7→3.0 through 3.3→3.4), split each workflow step into its own `workflows/*.md` file, added `references/ruby-patch-versions.md` and `references/multi-hop-strategy.md`, and added `templates/upgrade-report-template.md` plus `examples/simple-upgrade.md` and `examples/multi-hop-upgrade.md`. Strengthened Step 0 with an explicit rationale for why Ruby specifically targets the latest patch of a minor: patch releases within a minor accumulate deprecation warnings for the *next* minor's removals, so an old patch's Step 2 sweep can pass clean and still miss real breakage — a different reason than a Rails patch bump's (mostly security/bug fixes).
- Initial version of the skill. Sequential, one-Ruby-minor-at-a-time methodology mirroring `rails-upgrade`, plus a Step 2 (mandatory) deprecation-warning sweep using `RUBYOPT="-W:deprecated"` before bumping. `references/known-gotchas.md` seeded with confirmed real findings from a live Ruby 2.7 → 3.2.11 upgrade (fastruby/audit): `Proc.new`-with-no-block removal (aws-sdk v2), `URI.escape` removal (paperclip → kt-paperclip fork), re-adding `spring` after a Ruby floor is met still needing `Spring.dangerously_allow_disabling_reloading`, Docker base-image OS moves invalidating old workarounds, host-platform `bundle lock` pollution, and default gems losing implicit availability.
